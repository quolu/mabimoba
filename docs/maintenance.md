# ベルチームへ渡す更新手順

## 内容を更新する

内容の正本は `content/portal.json`。`sources`、`articles`、`families`、`database`、`news`、`roadmap`、`glossary`、`social` はサイトの各画面と検索へ連動する。`changelog` は「サイトの更新情報」（`/updates/`）、ホームの新着欄、更新フィード（`/feed.xml`）になる。

1. 公式の更新・ガイドと日本語／韓国語のXを読み、対象がマビノギモバイルであることを確認する。
2. 韓国・繁体字版・日本版を区別し、出典URL・確認日・資料の基準日を登録する。Xは投稿者・投稿時刻・原文リンク・内容の種類を保存する。
3. 数値や解放条件は公式を優先する。プレイヤーの検証は検証条件を確認し、単独の投稿は攻略仕様の正本にしない。日本版への適用未確認を消さない。
4. 既存の記事・DBを更新し、変わった内容に関わるニュースを追加する。ニュースと各記事を両方確認する。
5. `updatedAt` と変更した記事の `checkedAt`、参照した出典の `checkedAt` を更新する。未確認の出典の確認日を一括変更しない。
6. `changelog` の先頭に、その日の更新を書く。書き方は下の「サイトの更新情報を書く」。
7. `npm run check` と `npm run build` を実行する。ビルドは出典参照、検索の掲載先、内部リンクとアンカーの欠落で失敗する。
8. `npm run dev` の画面で変更した記事と検索・分類を確認する。新規画像は実際に読み込めることを確認し、素材台帳に出典を追加する。

### サイトの更新情報を書く

2026-10-08にオーナーの依頼で設けた。読者が、前に来た時から何が増えたかを一目で分かるようにする。

- 1日につき1件。`date` は日本時間の日付で、新しい日付を配列の先頭に置く。同じ日に二度公開する時は、その日の件へ項目を足す。
- `summary` はその日の更新を一文で書く。`items` は読者に見える変更を一つずつ書く。
- `type` は「新しい記事」「記事の更新」「データの更新」「ニュース」「Xの情報」「サイトの改良」のいずれか。記事とニュースを先に、サイトの改良を後に並べる。ホームの新着欄は先頭の4項目を出す。
- `url` はサイト内のパス（`/guides/記事ID/`、`/news/#ニュースID`、`/community/#post-投稿ID` など）。リンク先やアンカーが無いとビルドが失敗する。
- 手順書の変更、公開確認の記録、内部の作り直しのように読者に見えない変更は書かない。
- `updatedAt` と `changelog` の先頭の日付が違うと、ビルドが `CHANGELOG_STALE` で失敗する。`updatedAt` を進めた日は必ず書く。
- フィードの項目のIDは `type` と `text` から作る。公開した項目の文を直すと、フィードリーダーには新しい項目として届く。

Xの調査は既存のxarticle connectorの `x_search` を使える。初版は日本公式 `MabinogiM_JP`、日本語「マビノギモバイル」、韓国語「마비노기 모바일」「마비노기모바일」に攻略・ルーン・アビス等の語を加えて検索した。短い種類分けはJevで行い、最終的な採否と検証は担当AIが行う。投稿・返信・follow・likeなどの操作は、このサイトの収集依頼には含まれない。

## 公開する

公開先・既存経路・配置先は `deploy/target.json` を読む。SSH接続、GitHubへのread権限、サーバー上の既存Cloudflare資格情報が必要。値をリポジトリやログへ複製しない。

1. 対象ファイルだけをcommitし、通常pushする。
2. cleanなcheckoutで `npm run deploy` を実行する。
3. `deploy` はoriginの既定ブランチの祖先であることを確認し、そのcommitからサーバーのコンテナを構築する。専用コンテナだけを更新する。
4. 初回だけCaddy・Tunnel・DNSに新規ホストを追加する。Caddyのtarバックアップ、候補の構文確認、reloadを実行する。共有コンテナは再起動しない。
5. HTTPSのhealthと既存サービスの到達が確認できた時だけ公開成功とする。バックアップと公開記録はサーバー上の `~/.local/state/mabimoba/` に置く。
6. 公開URLで変更したページ・検索・スマホ表示を確認する。公開の確認結果を残す。

ドメイン設定に既存の相違がある場合は明示エラーで停止する。失敗時に別経路へ自動で切り替えない。

## 戻す

内容・デザインの不具合は、原因を確認して修正commitを公開する。直前の正常commitへの切り戻しが必要な場合は、既定ブランチの祖先である40桁SHAを `npm run deploy -- <SHA>` に渡す。Git履歴は書き換えない。

初回ドメイン設定そのものを取り消す場合は、記録されたCaddyバックアップとTunnelバックアップを確認する。共有設定の復元で他のサービスの新しい変更を消さないよう、追加したホストだけを取り除く。DNSは追加したCNAMEだけを対象にする。

## 定期更新

毎日16:00（Asia/Tokyo）に、BellTeamの予定で更新担当（ルピー、`bot-ca9fed97`）が実行する。2026-10-07にオーナーが依頼した。ブラウザを開くたびにXや公式の新着が同期される仕組みは設けていない。

### 毎日読む情報源

上から順に読む。上ほど仕様の正本に近い。

1. 日本版公式のニュース4種（[お知らせ](https://mabinogimobile.nexon.co.jp/news/notice)・[アップデート](https://mabinogimobile.nexon.co.jp/news/update)・[イベント](https://mabinogimobile.nexon.co.jp/news/event)・[不具合対応状況](https://mabinogimobile.nexon.co.jp/news/knownissues)）。前回の実行以降に増えた告知を全件読む。不具合対応状況は個別ページが無く一覧だけで、2ページ目以降もある。件数、ステータス、最終更新日の変化を見て、記事 `jp-known-issues` を直す。
2. 日本公式X `MabinogiM_JP`。メンテナンス・不具合・告知の速報として読み、公式サイトの告知と照合する。
3. 韓国版公式の[アップデート](https://mabinogimobile.nexon.com/News/Update)・[告知](https://mabinogimobile.nexon.com/News/Notice)・[イベント](https://mabinogimobile.nexon.com/News/Events)。アップデートノートは木曜が基本。日本版より先行する内容として扱い、日本版への適用未確認を消さない。読み方は下の「韓国公式の読み方」。
4. 日本語・韓国語のX（プレイヤー投稿）。検索語は上の「内容を更新する」と同じ。不具合と攻略の観測として読み、単独の投稿を仕様の正本にしない。
5. 台湾・香港・マカオ版公式。サービス開始や大型更新などの節目だけ扱う。

### 韓国公式の読み方

韓国公式（`mabinogimobile.nexon.com`）は日本のIPから英語トップへ転送される。URLの形や言語ヘッダーを変えても同じで、BellTeamのコンテナとmain-serverの両方で確かめた（2026-10-07）。

オーナーが契約しているNordVPNの、ソウルのHTTPSプロキシを経由して読む。同日、一覧・アップデートノート・公式ガイドが韓国語の本文で取得できた。

- 取得は更新担当の席にあるヘルパー（`integrations/nordvpn/kr-fetch.py URL 出力ファイル`）で行う。認証情報はBellTeamの保存先から読み、リポジトリ・ログ・会話へ出さない。
- プロキシは `krNNN.proxy.nordvpn.com:89` の「Standard VPN servers」の台を使う。「Dedicated IP」の台は正しい認証情報でも407になる。
- 経由するのは韓国公式を読む通信だけ。一回の実行で読むのは、一覧と前回以降に増えた記事、変更を確かめる公式ガイドに留める。

プロキシが使えない日は、次の経路で確かめる。いずれも同日に動作を確かめた。

1. Naver検索の `site:mabinogimobile.nexon.com`（新しい順）。公式記事のURL・題名・掲載時期・本文冒頭の抜粋が取れ、掲載から数時間で載る。抜粋に無い部分を推測で補わない。
2. Xの `mobinorick`（非公式の告知転記アカウント）。公式アップデートノートの画面を章ごとの画像で投稿している。この経路で読んだ時は、転記元が非公式であることを記事の注記に残す。
3. 韓国App Storeの「마비노기 모바일」（販売元 NEXON Korea）の更新内容。クライアント更新ごとの公式の要約。
4. 韓国の攻略媒体（[Inven](https://mabimo.inven.co.kr/)）。媒体の記事とプレイヤーの掲示板投稿は出典の種類を分けて登録する。

本文を確かめられた公式資料だけ `checkedAt` を更新する。確かめられなかった内容を記事に書かない。

### 読めない情報源の扱い

台湾公式（`tw.nexon.com`）はCloudflareの確認画面で403になる（2026-10-07実測）。確認画面を回避する仕組みは作らない。

### 更新の範囲

2026-10-07にオーナーが、情報の更新に加えて次の変更も更新担当の判断で行ってよいとした。

- サイト構成の改造（ページの追加・統合・並べ替え、導線の変更）。
- 内容の薄いページへの画像の追加。
- デザインの変更。

画像は `AGENTS.md` の規則どおり `public/assets` と素材台帳で管理し、出典と権利者を表示する。構成やデザインを変えた時は、`npm run check`・`npm run build` に加えて、変更したページとスマホ幅の表示、検索、内部リンクをブラウザで確かめてから公開する。何を変えたかをオーナーへの報告に書く。

### 一回の実行

1. `git pull --ff-only` で origin/main に合わせ、`npm run check` と `npm run build` が通ることを確かめる。
2. 上の情報源を読み、前回の実行以降の変化を拾う。
3. 変化があれば「内容を更新する」「公開する」の手順で反映し、公開URLを確認する。反映した内容は `changelog` にも書く。
4. 変化が無い日は内容を変えず、公開もしない。`updatedAt` だけを進めない。
5. 結果（反映した内容、読めなかった情報源、公開したcommit）をオーナーへ報告する。
